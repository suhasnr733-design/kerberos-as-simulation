## 🎯 Project Overview

This project provides an educational, interactive web simulation of the **Initial Kerberos Authentication Server (AS) Exchange** (based on the principles of Kerberos V5 / RFC 4120).

The simulation models how a client securely requests initial credentials for the Ticket Granting Service without transmitting plaintext passwords across an untrusted network:
1. **Client Authentication Request (`KRB_AS_REQ`)**: The user submits their principal identity, requested service identity, a random nonce, and a timestamp.
2. **AS Verification & Key Derivation**: The Authentication Server looks up the client's record in the KDC database and derives the client's secret key $K_C$ and the service master key $K_{TGS}$.
3. **Session Key & TGT Construction**: The AS generates an ephemeral session key $K_{C,TGS}$, packages the Ticket Granting Ticket ($TGT$), and encrypts it with $K_{TGS}$.
4. **Encrypted AS Response (`KRB_AS_REP`)**: The AS encrypts the session key, nonce, and ticket metadata using $K_C$ and returns the response with safe educational telemetry.

## 🔐 Cryptographic Design

The backend uses the standard, maintained Python `cryptography` library with modern cryptographic best practices:

| Component | Implementation | Notes |
|---|---|---|
| **Key Derivation (KDF)** | PBKDF2-HMAC-SHA256 | 100,000 iterations, 32-byte (256-bit) key, salt: `f"{realm}{username}"` |
| **Symmetric Cipher** | AES-256-GCM | Authenticated encryption with 16-byte authentication tag |
| **Nonce / IV Generation** | Unique 12-byte (96-bit) nonce | Cryptographically secure random bytes generated per encryption |
| **Session Key ($K_{C,TGS}$)** | 256-bit random key | Base64-encoded, ephemeral session key |
| **Replay Protection Nonce** | 32-bit positive integer | Generated by client, echoed by AS in encrypted client part |
| **Clock Skew Window** | $\pm 300$ seconds (5 minutes) | Mitigates replay attacks by rejecting stale timestamps |

## 🔄 Simplified Kerberos AS Exchange Process

The backend implements the 11-step authentication flow:

```
Client (Alice)                              Authentication Server (AS / KDC)
      |                                                    |
      | -------- 1. KRB_AS_REQ (cname, sname, Nonce, T) -> |
      |                                                    | 2. Validate principal format
      |                                                    | 3. Validate realm & sname
      |                                                    | 4. Check timestamp freshness
      |                                                    | 5. Lookup user & derive K_C
      |                                                    | 6. Generate session key K_C,TGS
      |                                                    | 7. Construct TGT
      |                                                    | 8. Encrypt TGT with K_TGS
      |                                                    | 9. Construct client response
      |                                                    | 10. Encrypt response with K_C
      |                                                    | 11. Generate KRB_AS_REP
      | <------- KRB_AS_REP (Encrypted TGT + Enc_Part) --- |
      |                                                    |
      | -- Client decrypts Enc_Part using password -> K_C  |
      | -- Verifies Nonce matches request                  |
      | -- Extracts K_C,TGS and stores opaque TGT          |
```

## ⚠️ Security Limitations & Academic Disclaimer

- **Educational Purpose**: This implementation is designed exclusively for the academic requirements of **Cryptography & Network Security (BCS703)**.
- **Not RFC 4120 Wire Compatible**: Standard Kerberos V5 uses ASN.1 DER encodings, UDP/TCP transport over port 88, and specialized RFC 3961 encryption types (e.g. `aes256-cts-hmac-sha1-96`). This project uses JSON payloads over HTTP with AES-256-GCM for clean web inspection.
- **No Sensitive Leakage**: Passwords, derived keys ($K_C$, $K_{TGS}$), and unencrypted session keys are never returned in public API responses or log streams.
- **In-Memory Store**: The principal database (`alice@CANARA.EDU`, `bob@CANARA.EDU`) resides in memory for development and demonstration.

## 🧪 Testing Instructions

Run the 10 automated test scenarios using `pytest`:

```bash
cd backend
# Run all tests with verbose output:
.\.venv\Scripts\pytest.exe -v tests/test_kerberos.py
```

### Test Scenarios Covered:
1. **Valid AS Exchange**: Verifies complete protocol flow and presence of all 8 telemetry steps.
2. **Unknown Principal**: Asserts HTTP 404 with `KDC_ERR_C_PRINCIPAL_UNKNOWN`.
3. **Unsupported Service**: Rejects service principals other than `krbtgt/CANARA.EDU`.
4. **Stale Timestamp**: Rejects timestamps older than the 300-second clock skew threshold.
5. **Invalid Request Schema**: Verifies field constraints (negative nonces, short lifetimes, missing fields).
6. **Correct-Key Decryption**: Validates client-side decryption using Alice's derived key and matching session key inside TGT.
7. **Incorrect-Key Decryption Failure**: Validates that wrong passwords trigger authentication tag validation failure (`InvalidTag`).
8. **Unique Session Keys**: Asserts that subsequent requests generate completely unique session keys and nonces.
9. **No Sensitive Values**: Asserts passwords, master keys, and plain secret strings never appear in API responses.
10. **Existing Health Endpoint**: Verifies backwards compatibility of `/api/health`.
